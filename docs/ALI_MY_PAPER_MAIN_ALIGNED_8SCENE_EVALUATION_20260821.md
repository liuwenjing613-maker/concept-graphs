# ali-my 对齐论文 main 的 Replica 8 场景评测（2026-08-21）

## 结论

本次已完成 Replica 标准 8 场景（`room0`–`room2`、`office0`–`office4`）的 ali-my 全量建图与评测。每个场景使用 `0:2000:5`，即 400 帧、stride 5；语义和对象指标均使用与 main 相同的 GT、类别/提示词、匹配定义和评测实现，并在同一评测后端下重新评测 main 的官方 post-map。

`n_exclude=6` 的 8 场景池化语义结果中，ali-my 相比 main：mIoU **+2.78**、mRecall **+4.45**、mPrecision **+6.29**、mF1 **+3.80**、fwIoU **+4.27**、点准确率 **+7.85** 个百分点。

对象检索结果并非全面领先：ali-my 的 mR@1 / mR@5 分别比 main 高 **0.74 / 0.70** 个百分点，但几何覆盖率、R@1、R@5 分别低 **14.92 / 2.82 / 11.69** 个百分点。因此当前结果应表述为“语义分割整体优于 main，长尾类别均衡召回大致持平略高，但对象覆盖与总体召回仍落后”。

## 1. ali-my 与 ali-dev 的关系

两者的指标定义和评测器是相同的，但不能把 ali-my 数值直接写成 ali-dev 数值。

- 服务器 ali-dev HEAD：`72f5962822b5e8678a446f367a06df1a977d2a4d`。
- 本次 ali-my HEAD：`bff233ff004939d2ecf4ac5546f87cb7b7b16e60`。
- Git 关系为 `0 / 14`：ali-dev HEAD 是当前 ali-my 的直接祖先，无分叉，ali-my 多 14 个提交。
- 多出的提交主要是证据保留、审计、确定性和验证；其中还包含 `Handle empty filtered detection frames` 的健壮性修复。因此基础建图方法一致，但某些边界帧和随机性处理可能令冻结地图不完全相同。
- 证据 sidecar 开/关的专门 parity 回归为 PASS：68/68 个对象、canonical membership、对象字段、边拓扑和逐帧数量一致；`bbox_np`、`pcd_np`、颜色与 `clip_ft` 最大绝对差均为 0。

所以更准确的说法是：**本次结果是 ali-dev 基础算法上的 ali-my 分支结果；评测口径可直接对齐，但若要声称 ali-dev 与 ali-my 数值完全相同，仍需另跑同配置 ali-dev。**

## 2. 对齐协议

| 项目 | ali-my | main 比较基准 |
|---|---|---|
| 场景 | Replica 全部 8 个标准场景 | 同 8 场景 |
| 帧范围 | `0:2000:5`，每场景 400 帧 | stride 5 官方结果 |
| 预测地图 | ali-my HEAD `bff233f` 新建地图 | main 官方 post-map |
| 语义 GT | Replica Semantic GT | 相同 |
| 语义类别/提示词 | 官方脚本口径 | 相同 |
| 点匹配 | CPU SciPy `cKDTree` 精确 k=1 | 同一后端重新评测 |
| 对象 GT | ReplicaSSG GT，共 248 个 GT 对象 | 相同 |
| 对象分类 | 地图原生 1024 维 `clip_ft`；OpenCLIP ViT-H-14 提示词 | 相同评测器和权重 |
| 关系推理 | `make_edges=false` | 本轮不作有效关系比较 |

同一 cKDTree 后端重新评测 main 后，8 场景聚合值精确复现 main 已发布汇总：mIoU 24.85%、mRecall 40.65%、mPrecision 36.31%、mF1 30.41%、fwIoU 36.47%。这排除了评测后端不同造成的比较偏差。

这里的“对齐”指场景、帧密度、GT、指标和评测器对齐；ali-my 与 main 仍各自使用本方法产生的检测和地图，这才是正常的方法级 benchmark，并不是强制两者共享检测结果。

## 5. 不能有效测试或不能作结论的项目

| 项目 | 原因 |
|---|---|
| Predicate R@1 / mR@1 等关系指标 | 8 次 ali-my 建图均设置 `make_edges=false`，没有运行关系推理；evaluator 中的 0 只是空边输入的结构性零值。 |
| scene-graph object tag / possible tags | 没有 scene graph、caption、节点标签或候选标签输入；自动生成的 0 行不是有效模型性能。 |
| 8 场景 R1 人工错误率、R2 重测一致性 | 本轮为 benchmark 建图，关闭证据 sidecar，也没有为新增 6 场景做人工 endpoint 标注；此前 R1/R2 结果仍仅覆盖 room0 和 office0。 |
| ali-dev 与 ali-my 的严格数值等价 | 代码存在 14 个提交差和一项边界帧健壮性修复；需要在 ali-dev 上另跑同一 8 场景协议后才能严格判断。 |
| “ali-my 全面优于 main” | 语义指标整体更高，但对象覆盖率和 R@1/R@5 更低；现有结果不支持全面优于的结论。 |

## 6. 运行资源与完整性

- 8 场景按顺序单任务运行在 GPU1；启动前检查显存和利用率，在他人任务高负载时等待，没有并发挤占。
- GPU3 已知异常且用户明确禁用，全程未使用。
- 对象评测阶段观察到 GPU1 上原任务持续高负载后，主动切到 CPU；语义阶段仅用 GPU1 计算一次 OpenCLIP 文本嵌入，点匹配为 CPU 精确 cKDTree。
- benchmark 设置 `save_evidence=false`、`save_detections=false` 以控制磁盘占用。已有 evidence on/off parity 回归证明在测试样本中最终对象字段数值零差异。
